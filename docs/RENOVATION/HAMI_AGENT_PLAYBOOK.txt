WHAT HAMI IS (do not shrink it)
"Hami" (हामी) means "we".
Hami is a living economic intelligence and action system. It tries to understand reality, discover where
value is lost or left unrealized, work out what is actually true, act only when authorized, learn from
outcomes, and keep expanding its ability to create and capture real value.
  The loop:   Reality -> Evidence -> Action -> Outcome -> Learning
  The question underneath:  Where does value disappear, why does it disappear, can Hami recover it,
  and can that recovery be verified?
Hami does NOT begin with a product category. Not inbox management, not seller software, not credit,
not Viber, not any one market. Those are contexts Hami may work in.

WHAT HAMI KEEPS
The continuity of: what it observes, what it knows, what it does not know, what evidence supports a
belief, what capabilities it has really shown, what actions were authorized, what happened afterward,
what outcomes were produced, and what was learned.
AI models, APIs, channels, robots and payment rails are replaceable capabilities. They are not Hami.

HOW HAMI EARNS
Hami is NOT a conventional SaaS company. The principle: value created -> value verified -> Hami
captures a fair share. No default subscription. No upfront fee just to access unproven software.
The exact commercial mechanism must itself be discovered and proven in reality.

THE RULE FOR ACTING
Act only when authorized. Humans are important partners and authorization boundaries today. Autonomy may
grow as reality proves what is safe. It grows through recorded authorization, never by quietly changing code.

HONESTY
Real revenue today is Rs 0 and real customers are 0, and Hami says so. A failed experiment is valuable
information. Something not known is written UNKNOWN. Honesty is part of the system, not a slogan.

THE CURRENT EXPERIMENT IS NOT HAMI
Right now Hami is running Experiment 1: understand how real online transactions in Nepal actually
happen and where they die. The slow-reply idea is only a HYPOTHESIS. The conversations with sellers ARE
the experiment. If the evidence points to payment trust, or somewhere else, Hami follows the evidence.
Never force reality to fit the experiment. In the code the experiment lives only as a context pack
(packs/slow_reply_recovery.json) made of data inside the six primitives. It is not a product.

THE FUTURE
Verified records that others can trust (a seller, a buyer, a bank, a supplier, a family abroad) are a
POSSIBILITY, not a claim. Do not build future architecture just because it is attractive. Reality must
promote it first.

THE TEST BEFORE EVERY STEP
Ask: "Am I improving Hami's ability to understand reality and create verified value, or am I accidentally
turning Hami into the current experiment?"  If it is the second one, STOP and write a question.

WHERE THE CODE LIVES
In this repo. The project used to be called ForgeOS. Its name is now Hami, but the old name still appears
inside many files until the rename steps in Phase 2 are done. The public site is haminp.vercel.app.
Part of your first job is to find which folder makes that site.


THE TEN STOP SIGNS (they beat every step; if a step seems to break one, the stop sign wins)
 1. NEVER act on the real world. You may change code in this repo. You may NOT contact anyone, publish an offer
    or move money. The owner has authorized nothing external to you.
 2. NEVER spend money or add a paid service. Everything stays at zero cost. If something costs money, ask.
 3. NEVER show fake numbers as real. Public numbers count REAL rows with proof only. Everything else is
    TEST, MOCK or HYPOTHESIS. A number you cannot know is written NOT MEASURABLE, never 0.
 4. NEVER delete what the owner might want. Move it to archive/ instead. You may delete only junk you made.
 5. NEVER write a secret (password, key, token) in a file, a note, a log or your reply. Names only.
 6. NEVER work on the main branch. Work on the branch called renovation. Save small and often.
 7. NEVER touch what you do not understand: platform scripts, branding or injected tags from templates,
    server/, scripts/grok-pwa-*, public/__grok/. Do NOT edit AGENTS.md. Ask first.
 8. NEVER say "done" without proof. Done means YOU ran the CHECK and SAW it pass.
 9. NEVER do two steps at once. NEVER read ahead.
10. NEVER store a customer's name, phone number or email. Only random tokens.

WHEN YOU ARE STUCK

 A stuck agent that asks is good. An agent that guesses and breaks things is bad.

WORDS YOU WILL SEE
 branch      a separate copy of the work, so the main copy stays safe
 commit      a save point you can go back to
 tag         a named bookmark on a save point
 migration   a small file that changes the database in a safe, repeatable way
 route       one address of the API, like /api/health
 API         the part of the program that other parts talk to
 test        a small program that checks another program
 gate        a list of checks that must ALL be true before the next phase starts
 token       a random code, used instead of a real name or number
 fingerprint a short code (a hash) that changes if anything in the record changes
 REAL        happened in the real world AND has proof attached
 TEST        made on purpose to test the program
 MOCK        pretend data, used for demos and checks
 HYPOTHESIS  a guess we want to test
 ESTIMATED   a number we calculated but did not actually see
 ACTUAL      a number we saw, with proof
 NOT MEASURABLE   we cannot know it yet, and we say so
 REQUESTED   asked for, not done yet            BOOKED   done and recorded
 AUTHORIZED   the owner clearly allowed it, in a recorded grant

RULES FOR THE NEPAL DETAILS
 Money:  rupees, written the Nepali way:  Rs 1,00,000  (lakh and crore commas).
 Time:   stored in UTC, shown in Nepal time (UTC plus 5 hours 45 minutes).
 Words:  Nepali and English. Any Nepali sentence YOU wrote is marked needs_review until a Nepali speaker checks it.
