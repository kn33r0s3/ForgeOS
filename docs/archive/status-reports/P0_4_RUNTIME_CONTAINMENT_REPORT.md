# ForgeOS P0.4 — Runtime Containment and Truth-State Repair

**Status:** Implemented and validated locally.

## Objective

P0.3 established that the five action/experiment records were internal proposals generated by the worker’s orchestration path, not completed executions or measured business outcomes. The safe repair therefore preserves those records and history while preventing ordinary application startup from processing queued work automatically.

## Changes implemented

The native `start.sh` path now starts the backend and frontend without starting `backend/worker.py`. The existing worker remains available through the explicit opt-in command:

```bash
FORGEOS_ENABLE_WORKER=true ./start.sh
```

The Docker Compose worker remains unchanged functionally but is now assigned to the explicit `worker` profile. Ordinary `docker compose up` starts the API, frontend, and Caddy only. Worker execution requires:

```bash
docker compose --profile worker up --build
```

The dashboard also received a minimal truth-state correction. It no longer labels a planned approval-required action as `EXECUTING`; execution is shown only when an action has a start timestamp and has not completed. The summary card was renamed from `Actions proposed / run` to `Validation plans` with the status `PLANNED / TRACEABLE`, preventing planned internal records from being presented as executed work.

No action, experiment, outcome, revenue, or historical database row was deleted, reset, synchronized, or rewritten.

## Validation

The normal `./start.sh` path was run once after the change. It reported `Worker disabled for safe application startup`, started the API on port 8000, and started the frontend on port 3000.

The backend regression suite passed **128 tests**. The frontend production build passed with all 11 application routes generated successfully. The non-mutating live regression suite passed for `/health`, `/forge/runtime`, `/stats`, `/forge/money/revenue-breakdown`, `/forge/execution/actions`, `/opportunities`, `/forge/knowledge/list`, and all valid frontend routes. The expected invalid alias `/system-flow` returned 404.

Browser verification through `http://localhost:3000/` reached the real API-backed dashboard and showed:

- `QUEUED WORK`, rather than `EXECUTING`, because queued tasks exist but no worker is running;
- `Validation plans: 5` with `PLANNED / TRACEABLE`;
- `Actual revenue: $0.00`;
- `Truth audit` values loaded from the backend;
- planned actions shown as `Action proposed` and the recommendation marked `PLANNED` / awaiting owner approval.

A first browser pass through the native dev server exposed a stale Next.js development-manifest error. This was isolated from the source change by stopping the dev process, removing only generated `.next` output, performing a clean production build, and verifying the rebuilt `next start` output successfully. The production browser pass was clean.

## Deployment identity and scope limitation

The local native path uses `storage/forge.db` through `DATABASE_URL=sqlite:///../storage/forge.db`. The Docker path mounts the host `storage/` directory into `/app/storage`. The public Caddy path proxies `/api` to the container backend and serves the frontend from the container network. No authenticated deployment connector or authoritative public-host shell was available to prove that the currently public instance has the same database file or the new source revision. The P0.4 change therefore updates the repository’s authoritative startup configuration but does not claim that an already-running public tunnel has been redeployed.

## Explicit worker behavior

The worker functionality is preserved. It is no longer an accidental side effect of ordinary application startup. Enabling it is an explicit operator decision through either `FORGEOS_ENABLE_WORKER=true ./start.sh` in native mode or `docker compose --profile worker up --build` in Docker mode. Because the worker can create internal cycle/proposal records, it was not started during this validation.

## Files changed

- `start.sh` — default-safe native startup and explicit worker opt-in.
- `docker-compose.yml` — worker moved to the explicit `worker` profile.
- `frontend/app/page.tsx` — planned-versus-executing truth-state correction.
- `P0_4_PRE_CHANGE_SNAPSHOT.json` and `P0_4_POST_STARTUP_SNAPSHOT.json` — read-only evidence.
- `P0_4_RUNTIME_CONTAINMENT_REPORT.md` — this report.

## Remaining recommendation

Deploy the updated repository through the authoritative production process, then verify the public instance’s revision and database identity before enabling the worker. If the worker is enabled, treat its output as proposed/internal activity until an approved execution and canonical measured outcome are recorded.
